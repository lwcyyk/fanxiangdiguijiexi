# 域名中心图文安装手册

## 1. 读者和边界

本文供现场实施人员使用，目标是在无互联网的受控网络中，把域名中心站点包安装到一台 R1 和可选的 R2/R3 主机。文中的框图可以直接与机柜、网络区和变更单逐项核对。

离线安装器负责校验和安装已经批准的制品，但不能代替以下外部工作：提供真实主机和网络、签发证书、生成并安全传递秘密、发布链上 Root/identity/Endpoint、安装真实 Resolver 内部 Trace、配置防火墙/VIP/监控/备份，以及批准生产切流。缺少这些材料时，证据必须记录 `blocked`，不得用 Mock、示例值或公网临时资源冒充。

## 2. 看懂安装拓扑

### 2.1 正确结构

```text
客户端 --(正式切流后 UDP/TCP 53)--> VIP
                                     |
                                     v
                              R1 Wrapper
                          Shadow: UDP/TCP 1053
                                     |
                                     v
                         R1 Resolver + Trace
                                     |
                    +----------------+----------------+
                    |                                 |
                    v                                 v
             公共 DNS 层次                    同一链路 R2 Resolver
                                                     |
                                             R2 Agent + Trace
                                             （没有 Wrapper）

每台主机：Registry Sync -> 本机 SQLite <- Agent/Wrapper
Hub：治理、签名、制品；不在 DNS 查询路径中
```

R1 是客户端入口，因此可以拥有 Wrapper。R2/R3 只作为上游节点，安装包的文件树、Compose 服务、profile、环境变量、端口映射和运行容器中都不能存在 Wrapper。仅把 Wrapper 设置为停止状态不合格。

### 2.2 网络边界

```text
允许：客户端/VIP -> R1 Wrapper          UDP/TCP 53（切流后）
允许：Shadow 客户端 -> R1 Wrapper       UDP/TCP 1053
允许：R1 Wrapper -> R1 Resolver         UDP/TCP Resolver 端口
允许：R1 Agent -> 同链 R2 Agent         TCP 8443，mTLS + peer Token
允许：Registry Sync -> 只读端点         受控管理网
禁止：Agent 或 Wrapper -> Registry/Norn 写接口
禁止：R2/R3 暴露 Wrapper
禁止：跨独立链路共享 SQLite、密钥或 Token
```

## 3. 准备阶段

### 3.1 双人核对交接介质

把介质接入受控主机前记录介质编号、交接人和时间。安装包至少应有归档、发布清单、SHA-256 清单、离线镜像以及目标主机/角色声明。

```text
[离线介质] --只读交接--> [受控暂存目录]
      |                         |
      +-- SHA-256 纸面/签名值 --+-- 本机复算并双人核对
```

摘要不同，停止。不要重新下载，不要忽略错误，不要尝试“修复”归档。

### 3.2 核对主机和角色

在每台机器上确认：

- 当前实际主机名与包内 `expected_host` 完全相同；
- 包内角色与变更单一致：R1/`first-hop` 或 R2/R3/`upstream`；
- 管理地址、Resolver 地址和证书 SAN 属于这台机器；
- 系统时间、磁盘、inode、文件描述符和 Docker/Compose 满足预检；
- 原 Resolver 配置位置已确认，备份目标盘不与数据盘混淆。

主机名不匹配时向导必须在载入镜像和改配置前退出。不得通过临时改 hostname、复制别的主机状态文件或使用跳过参数绕过。

### 3.3 Management secret 交接格式

Management 使用专用 `root:root`、`0700` 目录和 `root:root`、`0600` 文件。两个 issuer 文件必须是未加密 PKCS#8 PEM Ed25519；`publication-ssh-identity` 必须是未加密 OpenSSH Ed25519。安装器会实际解析密钥、派生公钥并拒绝 RSA/ECDSA、普通文本、加密文件、损坏文件、issuer 重复或 SSH/issuer 复用。生产秘密必须由带外流程提供。

测试实验只能显式执行：

```sh
sudo python3 tools/generate_management_secrets.py --secret-dir /绝对路径/test-secrets --test-only
```

命令只输出文件名、权限和公钥指纹，并标记 `TEST ONLY — NOT FOR PRODUCTION`；默认不覆盖已有文件，生成内容不能提交、复制到 Evidence 或用于生产。


## 4. 安装阶段

### 4.1 解包和预检

只使用发布方给出的安全解包步骤。安装器必须拒绝归档中的绝对路径、`..` 越界、符号链接/硬链接逃逸和设备文件。解包后先运行包内向导的帮助与预检功能，再执行安装。

预检结果示意：

```text
[通过] 发布摘要与 SHA256SUMS 一致
[通过] 实际主机名 = expected_host
[通过] 镜像引用全部固定到 sha256 digest
[阻断] 真实 Resolver Trace 插件尚未交付
[未运行] Wrapper Shadow 验收（前置条件阻断）
```

`blocked` 表示需要外部人员或外部系统补齐的条件；`not_run` 表示因为前置失败/阻断而没有执行。两者都不是成功。

### 4.2 离线载入镜像

安装器应调用本机 Docker 载入归档，禁止 pull。载入后还要检查实际镜像的 RepoDigest 与发布清单一致；“归档文件 SHA-256 正确”不能替代“镜像 digest 正确”。任何 `latest`、仅 tag 引用、短 digest 或载入结果不一致都必须停止。

测试和验收可使用 fake Docker，但现场证据必须来自真实主机 Docker。fake Docker 只能证明安装逻辑，不证明生产镜像已运行。

### 4.3 分阶段启动

```text
阶段 1  Registry Sync ----ready----+
阶段 2  Agent + Trace Adapter -----+--> Resolver Trace 就绪
阶段 3  Resolver ------------------+
阶段 4  R1 Wrapper Shadow 1053（仅 R1）
```

不能用 Compose 的 `service_started` 代替 readiness。每一阶段成功后，向导把输入摘要、完成时间和结果原子写入安装状态。若断电或人工中断，重新执行同一安装命令；向导读取状态，从首个未完成步骤继续。

重复运行时应满足：

- 已安装的相同版本不重复载入/重建；
- 不重新生成密钥，不覆盖外部秘密；
- 不删除 SQLite、Trace spool 或 Resolver 数据；
- 不重复修改已正确的配置；
- 输入或摘要改变时明确要求升级/重新审批，而不是静默复用旧状态。

## 5. Shadow 验收

### 5.1 R1 端口

R1 Wrapper 的 Shadow 只监听批准地址上的 UDP/TCP `1053`。此时客户端正式 UDP/TCP `53` 仍指向原系统。

```text
正式流量：客户端 -> 原 DNS 入口 :53
Shadow：  测试机 -> 新 R1 Wrapper :1053 -> 新 R1 Resolver
```

分别执行批准的 UDP、TCP、冷缓存、热缓存和（如适用）R1→R2 查询。记录查询标识、结果摘要、Trace 关联、证据状态和时间；日志中不记录 Token 或完整秘密。

### 5.2 失败关闭

依次验证 Trace 缺失、Agent 不可用、Registry 过期、证书/Token 错误、身份撤销、上游超时和证据不一致。任何一种情况下 Wrapper 都不能释放原始 DNS 响应，只能返回 `SERVFAIL`。禁止把关闭验证当成排障手段。

### 5.3 R2/R3 结构核验

检查安装归档和解包树、Compose 渲染结果、环境变量、开放端口和容器列表。应完全找不到 Wrapper。验收证据应写“结构不存在”，不能只写“Wrapper 未启动”。

## 6. 切流、观察与回滚

只有所有本地检查通过，且真实外部条件均有证据后，才可按批准比例 `1% → 10% → 50% → 100%` 切流。观察 SERVFAIL、延迟、Trace spool/dead-letter、Registry staleness、SQLite、CPU、内存、磁盘和容器重启。

达到变更单中的阈值就停止放量并回滚：

1. 停止新增流量并保存安装状态；
2. 将 VIP/入口切回原 Resolver；
3. 确认 Wrapper 已无生产请求后停止 Wrapper；
4. 保留 SQLite、日志、证据和原配置备份；
5. 采集脱敏支持包，交由授权人员分析。

生产主机禁止执行 `docker compose down -v`。普通回滚不删除数据，也不撤销链上身份。

## 7. 结果怎么写

每项证据使用固定状态：

| 状态 | 中文含义 | 使用条件 |
| --- | --- | --- |
| `passed` | 通过 | 检查真实执行且满足要求 |
| `failed` | 失败 | 检查已执行但不满足要求 |
| `blocked` | 阻断 | 缺少必须由外部提供/批准的条件 |
| `not_run` | 未运行 | 因前置失败、阻断或不适用而未执行 |

示例：

```json
{
  "status": "blocked",
  "status_zh": "阻断",
  "reason_zh": "缺少现场签发的 R1 Agent mTLS 证书",
  "requirement_owner": "现场 PKI 负责人"
}
```

安装包生成成功、本地 fake 探针通过或单机安装完成，只能表述对应范围。真实 Trace、网络隔离、现场负向测试、监控、备份、容量和变更审批未完成时，不得声称“域名中心部署完成”或“生产流量已启用”。
