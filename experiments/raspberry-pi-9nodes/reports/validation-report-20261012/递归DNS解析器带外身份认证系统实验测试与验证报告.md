## 实验成果摘要

系统已在受控物理平台实现并验证查询相关的解析器身份检查、响应绑定与授权非复用。其技术路线是在保持标准 DNS 报文格式的基础上，将候选贡献链、独立接纳并固定的身份视图、最终客户端响应和 Root 持久化授权状态共同纳入受控放行决定，限制身份不合格声明、响应替换和重复授权。

实验覆盖 RQ1–RQ5 五类问题。RQ1 的2,200个测量 Root 满足指定功能检查；RQ2 的1,700个负向案例在各自入口均被拒绝，其中200个为真实 DNS 决策、1,500个为隔离生产函数案例；RQ3 完成700个本地负向案例、70个正常对照及24,000个组件构造/分组；RQ4 完成302次故障活动及七个独立恢复块，700个恢复查询成功；RQ5 完成26条件、130对、260块和30,600个测量请求。

结果支持指定接口与工作负载下的身份政策拒绝、精确响应检查、Root 授权非复用和场景恢复。默认1 QPS 的 D3 hot/cold 成功回答 P50 成对倍率为5.95–9.17，反映认证部署整体开销，串行与流水线比较没有一致加速。报告完整保留四个历史多签名方组件接受案例、49次不确定超时和133个测量失败；near 有效回答为480/600，含一个0/120块。真实远端执行归属及生产级保证仍未建立。实验结束时的恢复与 writer0 依据封存回执，不代表当前现场核验；正式验收须结合已确认门槛与人工审核。

# 第一章 绪论与实验概述

## 1.1 项目背景与建设目标

客户端通常只看到 DNS 查询与回答，难以从标准 DNS 消息中识别递归过程中各个受管解析器的身份。转发配置、缓存、重试和传输回退会影响一次回答所对应的实际记录链。即使配置中的服务器地址仍可达，其身份也可能已经撤销、停用、换钥或不再符合端点政策。仅确认首跳连接对端，或对配置集合进行一次可复用批准，不能直接说明本次回答所关联的全部候选参与声明均符合当前采用的身份政策。

项目将标准 DNS 数据路径与带外身份检查路径分离。DNS 处理仍使用标准报文，额外的执行上下文、身份状态和授权记录通过控制接口及本地 Store 传递。工程目标是在受管配置内，把一次查询的候选贡献链、独立接纳的身份视图、最终面向客户端的响应和 Root 的持久化授权状态一起约束起来，避免身份检查通过后任意换用回答或重复消费授权。

这里的“候选贡献链”是系统根据执行记录构造并验证的参与声明，不自动等于独立证明的真实远端来源。系统不以额外证明 DNS 内容本身正确为主要研究目标。合法受管解析器按规定信任模型正确执行协议，DNSSEC 与身份政策分别承担数据真实性和受管身份检查职责。

## 1.2 实验目的与报告范围

实验围绕五个问题展开：候选执行记录能否跟随深度、缓存和传输变化；独立身份视图能否拒绝不合格声明；授权能否约束本查询的最终响应且不得复用；依赖故障如何影响新查询和恢复；认证部署与调度方式带来多大服务代价。报告同时整理正式结果和影响解释的历史异常，不把早期计划规模写成完成规模。

报告以已完成实验及冻结证据为依据，通过只读资料审计、结果核对和图表整理形成验证结论，不引入新实验或新的成功判据。配对增量来自既有数据，原始记录、历史失败、有效前缀和前期论文材料均保留，确保结果可追溯。

资料来源包括工作区工程记录、物理实验目录、正式归档、既有原始索引、接口与源码对应说明、冻结统计包和论文 Supplement S1–S6。主要目录和完整 SHA-256 见独立的《实验数据与证据索引》。为防止复制敏感信息，本报告不收录私钥、控制凭据或账号认证材料。

# 第二章 系统架构与技术方案

## 2.1 两条链路及组件职责

正常 DNS 链路由客户端、入口 Wrapper、受管递归解析器 R1–R3 和 AuthDNS 构成。D1–D3 是配置深度；缓存命中可能在 R1、R2 或 R3 结束本次记录链。带外链路包括 Trace Producer、Adapter、Agent、Registry Sync、Norn 身份后台与持久化 Store。身份后台回答身份是否合法，不承担“哪台服务器实际产生了某个普通 DNS 到达”的来源证明。

Producer 在本地观察请求及选中操作。Adapter 将授权登记与事件交给 Agent。Agent 维护上下文并签署本地证据。Graph 汇集候选链及引用关系。Wrapper 先验证结构一致性，再用独立 accepted view 检查固定候选中的身份声明；候选含有不合格身份时，不能删除该声明后继续把同一候选视作合格。Store 持久化证明消费和 Root 授权，响应对象在发送前仍需核对并消费。

## 2.2 单次查询与身份认证过程


![图2-2 单次查询、身份检查与响应放行](报告图表/2-2_flow.png)

图2-2 单次查询、身份检查与响应放行

来源：E-MAP；group W 响应顺序


入口为受保护查询建立 Root、Attempt 和入口 Context，授权控制接口负责登记。解析器在本地选定上游操作后、网络发送前完成必要登记，随后报告响应、失败和终止等事件。重试产生新的 Hop，不能把失败分支当成最终贡献来源。缓存命中声明当前回答解析器为终端，而非认证历史缓存填充链。

在响应准备阶段，Wrapper 核对入口回答的预期信息，验证 Graph 的签名、引用和与本请求的绑定，固定独立接纳的身份视图并检查候选声明。响应放行顺序为：收到入口响应并检查预期信息，恢复客户端 TXID，固定最终 client-facing 字节 r，提交 Root 授权，获得受控响应对象，发送前重新检查并消费该对象。授权提交不是客户端已收到回答；消费后崩溃可能导致未发送，却不能自动取得第二次授权。

## 2.3 标识、challenge 与摘要

Root 表示一次入口查询的授权对象；Attempt 表示相关尝试；Context 和 Hop 标识局部登记和操作。TXID 是 DNS 相关字段，长度有限且可复用，不能单独替代执行标识。相同报文摘要也不自动证明两个操作属于同一次执行。已有 Context/Hop 冲突测试检查保留行不能被覆盖，Root-only 消费状态则约束授权非复用，两者不能混为一项。

challenge 在 Wrapper evidence request 中提供，用于证据一致性检查。Graph 将返回值与预期请求值及执行对象一起核对；recursive-child consumption 另有保留的 challenge/terminal reservation。现有说明支持字段与检查位置，没有建立所有构建中该值的生成算法、固定时点或完整生命周期。不得把“请求提供了值”写成“已确认使用特定随机生成方案”。

普通 dns_wire_digest 的接口规范是将 DNS 消息 TXID 字节置零后做 SHA-256，保留其他字节。历史 cache-object 规则还清除 RR TTL，属于不同对象，不能代替普通 wire digest。最终响应授权采用恢复客户端 TXID 后的精确字节承诺。前两类用于相关与缓存对象描述，后一类约束最终输出；普通摘要规范与所有历史构建的完整对应仍有范围限制。

## 2.4 独立身份视图和验签路径

身份对象包含 server_id、角色、DNS 与 Agent 端点、生命周期/有效期及 AgentBinding 中的 key_id、算法、公钥、服务 URL。身份对象签发者凭据与 Agent 证据签名密钥不是同一用途。Graph 结构验签成功表明相应签名在选用公钥下有效，不直接说明身份已被独立权威接受。

已有 group W 对应材料确认：Graph 外层采用入口节点绑定，hop 采用源节点绑定，存在 target attestation 时采用对应目标节点绑定；检查 key_id 和 Ed25519 后验证签名。同一 Graph 的顶层 graph.nodes 进入 Wrapper 独立身份 join，以 carried/local 完整身份对象比较，包括 AgentBinding。该关系是指定源文件集合的对应，不能推及所有历史可执行程序或每个实验过程。

Wrapper 固定的是已经 accepted 的本地视图，不接受 Graph 内嵌 Registry 替代配置的身份权威。授权使用此前固定的视图及规定的新鲜度检查，不要求提交时必须等于本地最新 generation。新撤销视图到达并不自动改写已经 pinned 的查询决定；是否继续还取决于该旧视图的新鲜度及其余检查。

## 2.5 信任前提与适用范围

既有模型保留 A1–A4：签名与身份材料满足规定认证前提；入口 Wrapper 和受控响应对象按规定执行；本地观察和关联路径忠实；持久化授权状态受到保护。准确数学语义沿用现有主文，报告不新增更强假设，也不把 A3 解释成任何关联算法必然正确。

正常放行定理给出规定假设和检查下的必要条件。记录闭合、身份视图匹配、精确字节授权及 Root 非复用，不直接推出完整 AuthenticatedResponse。一般远端发送与目标本地到达的归属尚未建立。现有资料未展示客户端可见绕过，但“未展示”不能替代来源证明。控制观察 hook、Agent 或证据签名权限后，也不能依赖记录一致性保证被改写历史真实。

原型支持受管固定转发、当前缓存终端、规定重试和 UDP TC/TCP 继续。它拒绝未解决的多候选歧义，并限制部分缓存合成。普通 DNS 报文不插入项目字段，但不能因此称全部 DNS 并发、多来源、CNAME 或缓存行为完全透明。正向未登记外部终端、一般动态多上游、完整取消/迟到到达矩阵没有本轮正式完成证据。

实验结论：观察到指定状态发布与后续拒绝/恢复，属于相应记录下 PASS；瞬时全球撤销、传播上界、全部在途查询必须使用最新视图均 NOT TESTED。已 pinned 旧视图仍可能在满足 freshness 和其余条件时正常完成。证据：E-RQ2-PUB、manifest、逐 episode timestamp/transaction 和最终视图。

## 5.5 RQ3 精确响应替换与跨查询拼接

实验目的：身份接受之后，约束最终回答字节和查询关联。环境：真实 DNS 来源执行支撑的本地定向入口，不替换在线 DNS 服务。预期：准备后的响应不可被替换，另一 Root 的记录不能套用到本 Root 的 Graph 验证。

## 5.6 RQ3 更换 challenge 与消费后重开

实验目的：检查同一 Root 不因更换 challenge、Attempt 或进程重开获得新授权。方法：在原 Root 已消费且合法原响应保留的条件下再消费；另在 durable consume 后、emit 前让专用测试进程退出，重开同一 Store，再尝试消费。线上服务不因这些专用过程被整体重启。

实际结果：changed-challenge 的100/100负向再次消费被拒绝，10/10对照完成；crash/reopen 的200/200被拒绝，20/20正常对照完成。与响应替换和 cross-Root 合计700个本地负向、70正常对照。这些次数来自不同入口，不能以“700次全端到端放行攻击”概括。

分析：Root-only guard 与 proof 在同一持久化事务中提交，正常 Context purge 不删除 Wrapper guard。普通 Context 行被回收后重新登记不等于再次 Root 授权。持久化状态被保护且 guard 保留时支持 at-most-one logical authorization；不保证客户端一定收到一次，也不覆盖管理员删库、回滚或违反持久化假设。

changed-challenge 进入的是已消费 Root 的 Store，拒绝支持 Root 级非复用，不是 challenge 生成、新鲜性、不可预测性或单独 equality 检查的完备验证。实验结论：上述指定非复用/重开入口 PASS。证据：E-RQ3-L02、E-RQ3-L03及 Store/专用进程记录。
