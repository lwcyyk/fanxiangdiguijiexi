# Production Resolver Trace requirements

## Scope

This stage integrates exactly one resolver:

- Resolver: Knot Resolver 6.3.0
- Upstream tag: `v6.3.0`
- Upstream commit: `124d9357dc1c7c1b87f9eb40b4d1b225c3d1132e`
- Delivery base: `d62a157e0469bcc38de59972166279c912bd856b`

No second resolver, production server, live DNS cutover, PR merge, or formal
release is in scope.

## Required behavior

The trace source MUST be the resolver's real request and transport lifecycle.
For every request it MUST report:

1. the accepted client query;
2. every actual upstream send, including the exact DNS wire bytes and socket
   destination;
3. every matched upstream response;
4. transport failures, timeout retries, and UDP/TCP or endpoint switches;
5. cache-only completion;
6. the exact response returned to the client.

Each resolver request receives a cryptographically random trace ID. Events use
a monotonically increasing sequence and causal `parent_event_id`. Upstream
responses bind to a concrete outbound attempt. The implementation MUST NOT
associate requests by qname, DNS transaction ID alone, time windows, packet
capture, or "most recent" response selection.

## Security requirements

- Resolver hook, Trace Producer, and Trace Adapter communicate only over local
  Unix sockets.
- Every server uses a fixed producer UID/GID and mode-restricted socket
  directory.
- The Trace Producer acknowledges a resolver hook only after the Trace Adapter
  has durably spooled the event.
- Missing sockets, invalid frames, duplicate or out-of-order events, digest
  mismatch, full spool, producer failure, and Adapter failure close DNS
  processing.
- Trace records contain digests and routing metadata, not complete DNS payloads.
- The Trace Producer MUST NOT access Norn, another chain, Registry RPC, or
  SQLite.
- Registry Sync remains the only Norn client. Agent and Wrapper read the local
  trusted SQLite snapshot.
- Existing identity, mTLS, token, Registry freshness, endpoint, and
  fail-closed checks MUST remain enabled.

## Delivery requirements

The resolver-link package MUST support `first-hop` and `upstream`. It includes:

- the pinned Knot Resolver image reference;
- `ri-knot-trace-producer`;
- generated resolver integration configuration;
- preflight and configuration validation;
- backup, install, upgrade, rollback, and uninstall integration.

R2/R3 MUST NOT run Wrapper. Installation MUST back up an existing resolver
configuration before activation. A failed configuration check MUST NOT restart
the resolver. Upgrade, rollback, and uninstall MUST preserve both the original
configuration and its recorded backup without deleting resolver cache, Registry
SQLite, or Trace spool data.

## Acceptance and failure conditions

`production_trace_ready=true` may only be generated by the acceptance runner
when all of these pass with a real Knot Resolver process:

- UDP and TCP;
- same-qname concurrency and repeated client transaction IDs;
- timeout/retry and UDP-to-TCP;
- cache hit;
- CNAME chain;
- multiple-upstream switch;
- unavailable socket, full spool, producer crash, duplicate/mutated Trace;
- resolver restart, Agent unavailable, and stale Registry;
- end-to-end allow and fail-closed behavior;
- installation, upgrade, and rollback;
- full CI and secret scan.

The acceptance runner records concurrency and cross-trace counts. Any missing
scenario, non-zero cross-trace count, unverifiable image, manual success flag,
or security regression leaves `production_trace_ready=false`.
