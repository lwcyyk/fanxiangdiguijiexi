# Acceptance Criteria

This file defines the release-candidate gate. It does not carry forward results
from an older workspace. Machine-generated fresh-clone evidence is stored in
`acceptance.json`.

## Common adapter and storage

- [x] `RI_CHAIN_ADAPTER` is mandatory and accepts only `evm`, `norn`, or
  `external` (`ri-registry-sync/tests/configuration.rs`).
- [x] Selecting one adapter never falls back to another configured adapter
  (`selected_adapter_does_not_fallback_to_configured_norn`).
- [x] New and legacy EVM variable conflicts fail startup
  (`conflicting_new_and_legacy_evm_variables_fail_startup`).
- [x] Chain identity, Registry locator, schema hash, adapter metadata, height,
  hash, finality type, state root, and generation are explicit common fields.
- [x] Tagged adapter metadata rejects EVM/Norn/External type confusion
  (`typed_registry_reference_rejects_adapter_metadata_confusion`).
- [x] Existing schema-v2 EVM rows migrate without deletion
  (`schema_v2_evm_snapshot_migrates_without_data_loss`).
- [x] Target changes, checkpoint rollback, same-height hash changes, and
  generation rollback preserve SQLite, last-success heartbeat, and cache
  generation (`ri-store/tests/store.rs`).
- [x] Agent and Wrapper contain no chain-adapter/RPC dependency
  (`ri-registry-sync/tests/architecture.rs`).

## EVM

- [x] Chain ID mismatch, empty runtime code, runtime hash mismatch, specified
  block read failure, finalized fallback, checkpoint change, RPC ID mismatch,
  and oversized responses are covered by `ri-chain-adapter/src/evm.rs`.

## Go-Norn

- [x] Two unique RPC origins are mandatory; production requires HTTPS and mTLS.
- [x] Genesis, Registry address/key/schema, signer, validity window, signature,
  checkpoint, entry count, field size, and endpoint ownership are pinned.
- [x] The accepted height is the lower node head minus confirmations; insufficient
  confirmations, node disagreement, missing finalized publication, and scan
  exhaustion fail closed.
- [x] The local acceptance harness creates two data directories, two node keys,
  two mTLS read proxies, and rejects the native write method through those
  proxies.
- [x] `scripts/norn/05-negative-tests.sh` exercises live wrong pins, one node,
  unavailable verification node, insufficient confirmations, scan exhaustion,
  and failed-update preservation in addition to Rust security tests.

## External Sidecar

- [x] Exactly two independent HTTPS origins and complete mTLS client material are
  mandatory (`external_adapter_requires_two_independent_https_mtls_endpoints`).
- [x] The client disables redirects and rejects response-supplied upstream fields.
- [x] Both Sidecars must agree on the complete signed snapshot and historical
  checkpoint hash.
- [x] Chain identity, Registry locator, schema hash, signer, generation,
  validity, signature, state root, field limits, and checkpoint finality type
  are verified.
- [x] OpenAPI and JSON Schema use the same typed External target as Rust and the
  management CLI.

## Reproducibility gate

The final gate must run from a fresh clone with a unique Compose project and
new Norn data, node keys, TLS material, SQLite database, and acceptance output.
The required command results, test counts, image digests, Go-Norn revision,
genesis, Registry pins, plan hash, signed/synchronized checkpoints, cleanup
status, and secret audit result are generated by the Norn scripts into
`acceptance.json`; they are not hand-edited here.
